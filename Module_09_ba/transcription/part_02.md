
# 🚀 Архитектура автоматизации
**Тема:** Проектирование системы генерации документов (договоры, дипломы, направления на практику).
**Инструментарий:** SQL (SQLite), JSON, AI Studio (как среда прототипирования), Markdown.

---

## 1. Фундамент: Анализ бизнес-процессов (Business Analysis)
Прежде чем писать код, нужно понять **физическую реальность**. Excel — это кривое зеркало реальности. Наша задача — построить "скелет", который эту реальность отражает корректно.

### Путь пользователя (Student Journey Map):
1.  **Лид:** Человек на сайте/в рекламе.
2.  **Абитуриент:** Заполнил анкету, попал в базу.
3.  **Студент:** Заключил **Договор №1** (обучение).
4.  **Практикант:** Ему нужно **Направление на практику** (Договор №2).
5.  **Выпускник:** Получает **Диплом**.
6.  **Трудоустройство:** Попадает в базу выпускников.

**🔴 Главная боль (Pain Point):** Ручная подготовка документов.
*   *Сейчас:* Секретарь копипастит данные из Excel в Word. Это долго и чревато ошибками.
*   *Цель:* Кнопка «Сгенерировать договор», где данные подтягиваются автоматически.

---

## 2. Проектирование Базы Данных: Метод «Акинатор»
Чтобы спроектировать правильную структуру БД, нужно сыграть в «Акинатора» — задавать бинарные или уточняющие вопросы к реальности, чтобы отсечь лишнее.

**Ключевые вопросы для архитектуры:**
*   *Вопрос:* У студента один договор за всё время?
    *   *Ответ:* Нет, может быть договор на обучение, на практику, доп. соглашение.
    *   *Вывод:* Связь «Один-ко-многим» (1 Student -> Many Documents).
*   *Вопрос:* Договоры всегда одинаковые?
    *   *Ответ:* Нет, есть шаблоны (Учеба, Практика), и они меняются со временем.
    *   *Вывод:* Нужна сущность **Templates** (Шаблоны).
*   *Вопрос:* Данные (адреса, названия фирм) вводим руками?
    *   *Ответ:* Нет, это частые повторы.
    *   *Вывод:* Нужны **Справочники** (Dictionaries).

## 3. Архитектура решения (The Blueprint)

Мы не строим монолит («Звезду Смерти») сразу. Мы делаем **MVP (Minimum Viable Product)** для конкретной задачи — генерации документов.

### Сущности БД (Schema Design):

1.  **Students (Студенты):**
    *   ФИО, Личный код, Email, Телефон.
    *   *Логика:* Это "клиент".
2.  **Templates (Шаблоны документов):**
    *   Название (напр., "Договор на практику"), Текст шаблона (в формате Markdown).
    *   *Config Fields (JSON):* Самая хитрая часть. Чтобы не менять структуру БД под каждый новый тип документа, мы храним список необходимых полей (переменных) внутри JSON-объекта в одной ячейке.
    *   *Пример JSON:* `{"field": "place_of_practice", "type": "dictionary_ref"}`.
3.  **Dictionaries (Справочники):**
    *   Места практики (рестораны, отели), Юр. лица, Ответственные.
    *   *Зачем:* Чтобы секретарь выбирал "Hilton" из списка, а не вбивал адрес руками каждый раз.
4.  **Documents (Сгенерированные документы):**
    *   Связь со Студентом и Шаблоном.
    *   **Принцип неизменности (Snapshot):** Это критически важно!
        *   *Проблема:* Если студент сменил фамилию или мы поменяли шаблон *после* подписания договора, старый подписанный договор измениться не должен.
        *   *Решение:* В таблицу `Documents` мы сохраняем **статичный слепок** (готовый текст или PDF), а не просто ссылку на шаблон. Это наш цифровой архив.

## 4. Техническая реализация (The Engine)

### Гибридный подход: SQL + JSON
Мы используем реляционную базу (SQLite) для жестких связей и JSON для гибкости.

**SQL-схема (примерный код, упомянутый лектором):**

```sql
-- Таблица студентов (Жесткая структура)
CREATE TABLE students (
    id INTEGER PRIMARY KEY,
    name TEXT,
    personal_code TEXT,
    email TEXT
);

-- Таблица шаблонов (Гибкая структура через JSON)
CREATE TABLE templates (
    id INTEGER PRIMARY KEY,
    name TEXT,
    body_markdown TEXT, -- Сам текст договора с плейсхолдерами {{name}}
    fields_config JSON  -- Конфигурация: какие поля спрашивать у юзера
);

-- Таблица документов (Архив)
CREATE TABLE documents (
    id INTEGER PRIMARY KEY,
    student_id INTEGER,
    template_id INTEGER,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    final_body TEXT, -- Зафиксированный текст, который ушел на печать
    user_input_data JSON -- То, что ввел секретарь (для истории)
);

-- Справочники (Универсальная таблица)
CREATE TABLE dictionaries (
    id INTEGER PRIMARY KEY,
    type TEXT, -- например 'restaurant' или 'legal_entity'
    value JSON -- {'name': 'Hilton', 'address': 'Vanalinn 1'}
);
```

### Генерация документа (Markdown + Jinja style)
Вместо сложного форматирования Word используется **Markdown**. Это простой текст, который легко конвертировать в PDF.
*   *Шаблон:* `Я, {{student_name}}, обязуюсь...`
*   *Данные:* `student_name = "Ivanov"`
*   *Результат:* `Я, Ivanov, обязуюсь...`

## 5. Прототипирование интерфейса (Frontend в AI Studio)

Лектор предлагает использовать AI Studio для быстрой сборки UI, чтобы не тратить время на написание HTML/CSS вручную на старте.

**Алгоритм работы Секретаря (User Flow):**
1.  **Выбор студента:** Из выпадающего списка (Select).
2.  **Выбор типа документа:** Например, "Договор практики".
3.  **Заполнение переменных:** Система читает `fields_config` из шаблона и рисует форму.
    *   Если поле простое -> `Input text`.
    *   Если поле справочное -> `Select` из таблицы `dictionaries`.
4.  **Предпросмотр (Preview):** Генерация Markdown "на лету". Секретарь видит готовый текст, может поправить опечатки вручную (Human-in-the-loop).
5.  **Сохранение (Commit):** Нажатие кнопки "Сохранить".
    *   Генерируется PDF.
    *   Запись падает в таблицу `Documents`.
    *   Документ становится "вечным" (историческим).

## 6. Итоговые инсайты (Takeaways)

1.  **Не усложнять на старте:** Не надо пытаться автоматизировать *всё* (расписание, оценки, посещаемость). Начните с самого узкого горлышка — генерации бумажек.
2.  **Разделяй и властвуй:** Отделите *данные* (БД) от *логики* (Генератор) и от *представления* (Шаблоны).
3.  **Гибкость через JSON:** Если документы часто меняются, не делайте под каждый тип отдельную колонку в таблице. Используйте JSON-поле для атрибутов документа.
4.  **Справочники спасают время:** Никогда не позволяйте вводить одни и те же юридические адреса партнеров руками. Только выбор из списка.
5.  **Артефакт важнее шаблона:** Подписанный документ — это история. Его нельзя менять задним числом через изменение шаблона.
